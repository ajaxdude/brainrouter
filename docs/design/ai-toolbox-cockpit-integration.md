## Problem
brainrouter's dashboard/CLI today can only list and upgrade a single hardcoded podman toolbox (`docker.io/kyuz0/amd-strix-halo-toolboxes:vulkan-radv`, llama.cpp/Vulkan only). The user runs (or wants to run) additional inference backends — DS4 (DeepSeek4 GGUF), Halogen (HGN "Flash" bundles), vLLM (HF-repo serving), R9V (ROCm on AMD R9700) — that today can only be managed through `ai-toolbox-cockpit`, a Python Textual TUI with **no CLI or API mode** (`main.py`/`app.py` always launches the full-screen app; nothing is shell-out-able). The user wants brainrouter itself — its Rust dashboard and CLI — to become the primary, native interactive surface for managing all of these backends' toolboxes/models/servers, sharing cockpit's on-disk config and catalog data rather than re-inventing a divergent brainrouter-only store, and to surface backend/engine as first-class dimensions in brainrouter's existing Sankey diagram and benchmark system, plus a new spider/radar chart for comparing runs across dimensions including a **proposed** "token efficiency to positive result" metric.

## Goals and non-goals

**Goals**
- Native Rust (no Python/cockpit runtime dependency) toolbox lifecycle management (list/create/update/delete/enter-equivalent) for backends: `llama_cpp` (already partial), `ds4`, `halogen`, `vllm`, `r9v`, and future backends added to the catalog without a brainrouter code change for the *listing/catalog* path (server-mode/bespoke launch support for a brand-new backend still needs a follow-up PR — see Open questions #7).
- Explicitly **exclude `comfyui`** (image-gen, not coding-relevant) from every user-facing surface of this work, even though the catalog format itself must still be able to parse it without failing (see Technical plan §2).
- Read (and, per the user's explicit ask, eventually write) cockpit's `~/.config/ai-toolbox-cockpit/config.json` so both tools share one source of truth for backend defaults/active platform/default toolboxes, instead of a second brainrouter-only config. **Revised in v2:** the write half ships in a narrower, safer first form than v1 proposed — see Technical plan §4.
- Consume cockpit's `models.json`/`toolboxes.json` catalog as the data source for what toolboxes/models exist, their images, `runtime_profile`/`engine_args`, and per-model `toolbox_defaults`.
- Extend the Sankey diagram with two new columns: **backend** (which toolbox family served the request) and **engine** (which accelerator/runtime the toolbox used — vulkan/rocm/etc.).
- Extend the benchmark system so runs carry backend + engine as queryable/filterable dimensions.
- Ship a new spider/radar chart in the benchmark UI letting the user pick dimensions among: models, harnesses, token efficiency to positive result, speed, engine, backend, toolbox.
- Fix the stray untracked-container bug in the version-check code path as an early, independent, low-risk fix. **Revised in v2:** the root-cause mechanism is refined (see Technical plan §5a) — the original "missing `--name`" framing was incomplete.

**Non-goals (this round)**
- comfyui support (explicitly excluded by the user) — catalog parsing tolerates it, nothing else does.
- Full 1:1 feature parity with every cockpit TUI micro-interaction (e.g. its `SearchableSelect`/`SelectModal` widgets, ASCII banner, exact keybindings) — parity is scoped to *capabilities* (create/update/delete/list/launch/configure), not TUI widget fidelity, since brainrouter's surface is a web dashboard + CLI, not a TUI.
- Running/validating DS4, Halogen, vLLM, or R9V on hardware brainrouter's current dev/CI environment (Strix Halo, Vulkan/ROCm) can exercise end-to-end — see Risks.
- Rewriting the existing benchmark experiment/run schema (`runtimes`, `experiments`, `runs`, …) wholesale — we extend it (exact mechanism now an explicit Open question, see below), we do not replace it.
- A jointly-supported (brainrouter+cockpit) locking/conflict protocol for `config.json` — out of scope until upstream cockpit adopts one; see Technical plan §4.
- Wiring detached toolbox server-mode containers into brainrouter's actual LLM request router as fully first-class routable providers with health-checking/failover parity to Manifest/llama-swap — v2 adds a **minimal** registration/tagging prerequisite (Technical plan §5b) sufficient to populate Sankey/benchmarks honestly, not a full routing-parity rewrite.

## Current system

### Toolbox/podman management (brainrouter, today)
- `GET /api/toolboxes` → `toolboxes_list()` (`src/server.rs:1753-1809`) runs `podman ps -a --format "{{.Names}}\t{{.Image}}\t{{.Status}}"`, keeps only containers named `llama-*`, and enriches each with `local_created`/`latest_created`/`update_available` via `image_created_date()` (`:1825`) and `hub_toolbox_tag_dates()` (`:1839`, a Docker Hub tags-API poll — this is brainrouter's existing analogue of a "periodic fetch" pattern). Response is ad-hoc `serde_json::Value`; **no dedicated `Toolbox` struct exists**.
- `upgrade_toolbox()` (`src/server.rs:2257-2313`): `podman pull <image>` → `toolbox rm --force <container>` (result ignored) → `toolbox create --image <image> <container>`. Helper `toolbox_container_image()` (`:2244`) reads the current image via `podman inspect --format "{{.Image}}"`.
- Hardcoded default image `docker.io/kyuz0/amd-strix-halo-toolboxes:vulkan-radv` appears at `src/server.rs:527` (upgrade route default), `:1889` (version-check `podman run`), `:1919` (image inspect for version metadata), and the Docker Hub tag URLs at `:1842`/`:2044` hardcode the `kyuz0/amd-strix-halo-toolboxes` repo. There is **no backend/engine concept anywhere** in this code — it is single-image, single-backend by construction.
- **Confirmed bug, mechanism refined in v2 (see Technical plan §5a):** `src/server.rs:1886-1909` runs `podman run --rm --kill-on-drop docker.io/kyuz0/amd-strix-halo-toolboxes:vulkan-radv llama-server --version` with a 15s `tokio::time::timeout` (`PODMAN_VERSION_TIMEOUT_SECS`, `:1886`) and `.kill_on_drop(true)` (`:1890`) but **no `--name`**. v1 of this document asserted the missing `--name` itself was the leak cause; the Dory critic correctly pointed out `--rm` alone reclaims the container on a *normal* exit regardless of name. Re-verified directly: the real leak path is the **timeout branch** — when `tokio::time::timeout` fires, `kill_on_drop` sends the child process a kill signal, which can terminate the `podman run` client without giving it the chance to run its own `--rm` cleanup, potentially orphaning the container underneath. A fixed `--name` doesn't prevent that by itself, but it is still the right complementary fix: without a name, an orphaned container can't even be *found* to clean up (only a random pet-name); with a fixed name, an explicit `podman rm -f <name>` can be issued on the timeout branch as a real, targeted cleanup, and `--replace` prevents "name already in use" errors on concurrent/retried checks.
- CLI: `src/cli.rs:88-104` defines `Toolboxes` and `Upgrade { component }` (clap `PossibleValuesParser` limited to `["llama-swap","manifest","toolbox"]`); handlers at `:527-536` just proxy to `/api/toolboxes` and `/api/upgrade/{component}`. The CLI is a thin client that can target either a local UDS or a **remote** daemon via `--url` (`src/cli.rs:5-6,23-32,339-347`) — relevant to the "enter" design, see Technical plan §5.
- Config: brainrouter's own config is **YAML**, not JSON — `BrainrouterConfig`/`ManifestConfig`/`LlamaSwapConfig`/`ModelsConfig`/etc. in `src/config.rs`, resolved via `default_config_path()` (`~/.config/brainrouter/brainrouter.yaml`). There is no existing brainrouter JSON config and no existing reader for cockpit's `~/.config/ai-toolbox-cockpit/config.json` format. **Relevant risk already partially known to the codebase:** `src/daemon.rs` already warns at startup if `$HOME` is unset ("upgrade and version-check paths will fall back to /root", `src/daemon.rs:284-286`) — i.e. the daemon's process HOME/config resolution diverging from an interactive user's HOME is an already-acknowledged class of bug, directly relevant to config.json sharing (Technical plan §4).
- Existing destructive-route protection: `src/server.rs:224-241` gates a hardcoded path-prefix/exact-path allowlist (`/api/restart/*`, `/api/upgrade/*`, `/api/benchmarks/*`, etc.) to loopback-only callers. **New mutation routes this plan adds are not automatically covered** — each new privileged path must be explicitly added to this list, or it is reachable from non-local callers if the daemon binds non-loopback (`src/daemon.rs:144-153` — the daemon has an optional non-loopback bind mode). Confirmed by direct inspection.
- Terminology note (important, see Alternatives/Decision log): brainrouter's codebase already uses the words "backend" and "engine" informally elsewhere (routing profile backends in `src/routing_profile.rs`/`src/router.rs`, and UI copy). None of those are the toolbox/GPU-accelerator concepts this plan introduces — they are LLM-routing-provider concepts. This plan must not conflate the two; naming is addressed explicitly below.
- **Router/provider construction (new in v2, load-bearing for the Sankey/benchmark promises):** `src/daemon.rs:305-320` constructs the single shared `Router` from exactly `classifier`, `manifest`, `llama_swap`, and a handful of fixed routing knobs (`RouterArgs`) — there is **no generic "list of providers" or dynamic-registration concept** today. A detached, brainrouter-managed toolbox server container (Technical plan §5) is therefore **invisible to the router** unless something explicitly wires it in. This directly gates how much of the Sankey/benchmark "backend/engine reflects real traffic" promise can be true in the near term — see Technical plan §5b and Decision log.

### Sankey diagram (`src/escalation/templates/main_dashboard.html`)
- Fixed **4-column** schema: `SK_COLS = [harness@x16, session@x300, routing@x720, model@x1040]` (`:1314-1319`), total width `SK_TOTAL_W = 1232` (`:1325`).
- `skKeysOf(e)` (`:1411-1414`) returns exactly `{c0,c1,c2,c3}` from `skHarness/skSession/skRouting/skModel`; `skModel()` reads `e.model_key` / `e.effective_provider`, fields that come from `RouteEvent` (`src/routing_events.rs:30-82`, corrected citation — the struct itself spans `:30-82`, not `:23-63` as v1 stated).
- Rendering is **hand-rolled SVG**, not a chart library: `updateSankey()` rebuilds `svg.innerHTML` from computed node/link maps, draws Bézier `<path>` links and `<rect data-col data-key>` node bars.
- Click-to-filter state is `sankeyFilter = {col, key}` (`:1326`-ish); `matchesSankey(t)` compares `skKeysOf(t)['c' + sankeyFilter.col]`. Everything is keyed generically by column index (`c0..c3`, `SK_COLS[i]`), so **the mechanism itself already generalizes to N columns** — the concrete blocker to adding columns is (a) `skKeysOf()` hardcodes exactly 4 fields, (b) `skColorFor()` hardcodes a color map per column index 0–3, (c) fixed pixel `x` positions / `SK_TOTAL_W` assume 4 columns' worth of width, (d) the upstream data source (`RouteEvent`) has no backend/engine fields to key off today, and (e) — new in v2 — even once the fields exist on `RouteEvent`, **only requests actually routed through the Router will ever populate them**; detached toolbox-server containers launched from the new Toolboxes UI are not on that path today (see above).

### Benchmark system (`src/benchmark.rs`, `migrations/0001_benchmark_explorer.sql`, `migrations/0002_benchmark_lab.sql`, `src/escalation/templates/benchmarks.html`)
- This is a **mature, already-multi-dimensional** star schema: `models` → `artifacts` → `experiments` (joins `artifact_id`, `runtime_id`, `hardware_id`, `workload_id`) → `runs` → `performance_metrics`/`speculative_metrics`/`quality_results`/`telemetry_samples`.
- **Key discovery (changes scope of this plan materially):** `runtimes.backend` (`migrations/0001_benchmark_explorer.sql:58`) is already `CHECK(backend IN ('cpu','cuda','rocm','vulkan','metal','sycl','rpc','other'))`. That is *already* the coarse "engine" axis the user is asking for (vulkan/rocm, plus headroom for cuda/metal/sycl). `RuntimeDefinition` (`src/benchmark.rs:388-406`) and `RunSummary` (`:1748-1773`) already surface it end-to-end to the UI. We do not need a new column for this *coarse* axis — but v2 refines this (see Technical plan §1): cockpit's actual `runtime_profile` strings (e.g. `amd-rocm-hipblaslt`, `halogen-strix-halo`) are **finer-grained** than this 8-value enum and do not map onto it 1:1; the existing column remains the right thing to expose as the user-facing "Engine" (that's the granularity the user actually asked for — "vulkan/rocm"), but the finer profile id is tracked as a separate, non-benchmark-exposed field for toolbox deployment purposes only.
- What genuinely does **not** exist yet: a "which toolbox family served this run" dimension (ds4/halogen/vllm/r9v/llama_cpp). Nothing in `runtimes`, `experiments`, or `runs` names the *toolbox/serving stack*; `runtimes` today models a llama.cpp-fork-centric world with **`NOT NULL` fields** `repository`, `fork_name`, `commit_sha`, `compiler`, `compiler_version` (`migrations/0001_benchmark_explorer.sql:50-64`) that don't cleanly fit vLLM (HF-repo based) or DS4/Halogen (bespoke GGUF/HGN loaders) — these backends have no meaningful "compiler"/"commit_sha" in the same sense. This is a real, new dimension, and how to add it without breaking the existing `NOT NULL`/uniqueness contract is a genuine, not-yet-fully-resolved schema-design question (elevated to Open questions in v2 — see below; v1 asserted a specific `ADD COLUMN` approach that the critic showed was incomplete against the actual constraint).
- Ingest is `INSERT OR IGNORE` (`src/benchmark.rs:2248-2273`) keyed on `runtimes`' existing uniqueness — adding new dimensions to that table risks either (a) not being covered by the uniqueness key, so distinct toolbox-family runs collide/dedupe incorrectly, or (b) widening the uniqueness key, which can silently orphan a referencing `experiment_id` under `INSERT OR IGNORE` semantics if a near-duplicate row is ignored instead of inserted. Must be designed explicitly, not assumed safe by analogy to today's llama.cpp-only usage.
- **Migration runner is hardcoded and strict** — re-verified directly in v2: `src/benchmark.rs:1895-1953` only recognizes schema versions 1 and 2, requires an exact row/table-count match (`required_v1_tables != 5`, `required_tables != 6`), and returns `BenchmarkError::Validation` for anything else. A new `migrations/0003_*.sql` file **will not run** just by existing on disk — this function's version-gate logic must be extended to know about version 3 (and later 4), including its own expected-table-count check. This was flagged by the Dory critic as a concrete, load-bearing implementation gap (not a stylistic one) and is now called out explicitly in Detailed implementation.
- Outcome tracking already exists: `runs.status` (`succeeded|failed|oom|timeout|cancelled|skipped|...`) and `quality_results.passed`/`compile_succeeded`/`tests_passed`/`tests_total`. Token counts already exist per-run (`experiments.prompt_tokens`, `experiments.generation_tokens`) and per-quality-check (`quality_results.generated_tokens`). **No existing "token efficiency" or "tokens per success" metric anywhere in the codebase** — confirmed by search. **New in v2:** `experiments.prompt_tokens`/`generation_tokens` are, on inspection, the run's **declared/planned** token budget fields (populated at experiment-setup time), not necessarily an **observed, actually-consumed** count per attempt — this distinction matters a lot for a metric named "token efficiency to *positive result*" and must be resolved during implementation (see Technical plan §8 and Open questions).
- Charting is custom inline SVG (`scatter`, `drawBars`, `drawQuality`, etc. in `benchmarks.html`) — no chart.js/d3, and **no existing radar/spider chart** anywhere in the codebase. The spider chart is wholly new UI, not an extension of an existing chart type.
- Import path: `POST /api/benchmarks/ingest/llama-bench` (`src/benchmark/http.rs`) + `apply_llama_bench_metrics()` (`src/benchmark/imports.rs`) only reads throughput/ttft fields from `llama-bench.json`; backend/engine/toolbox identity must come from the **experiment/runtime template** the import is attached to, never from the llama-bench payload itself.

### ai-toolbox-cockpit (verified against the actual repo, not just the background brief)
- Entry point is `ai_toolbox_cockpit/app.py` (a Textual `App`), with three tabs backed by `views.py`: `ToolboxesView`, `ServersView` ("Server Mode"), `ModelsView` — confirming the three surfaces the user wants brainrouter to match/exceed.
- `catalog/schema.py`: `BACKEND_IDS = {llama_cpp, vllm, comfyui, ds4, halogen, r9v}`; `MODEL_KINDS` maps each backend to its model artifact kind (`gguf`, `gguf_file`, `hf_repository`, `r9v_package`, `hgn_bundle`, `workflow_bundle`). Per-backend model-entry validation is genuinely different per backend (llama_cpp: `inference_profiles`+`toolbox_defaults`+`auxiliary_downloads`; r9v: pinned 40-hex commit SHA + a fixed set of required file `role`s + a separately-hashed PLE file; halogen: `.hgn` checkpoint/overlay + tokenizer dir; vllm/comfyui validated elsewhere in the same file, not yet fully inspected). This confirms the README's claim that "each backend owns its model semantics" — a generic "download+run" abstraction will not fit all five; brainrouter needs a per-backend adapter, not one generic path.
- `assets/toolboxes.json` (`schema_version: 3`): a `runtime_profiles` map (named profiles like `amd-rocm`, `amd-rocm-hipblaslt`, `vulkan`, `intel-level-zero`, `nvidia-gb10`, `halogen-strix-halo`) each holding raw `engine_args` (podman `--device/--group-add/--security-opt/--env` flags) — **this is the actual accelerator/engine concept** in cockpit, distinct from `runtime/engines.py`'s `ContainerEngine` enum (`podman`/`docker`, the *container tooling* choice). A `toolboxes` array lists concrete toolbox entries: `id`, `backend`, `name`, `container_name`, `group`, `image`, `channel` (`stable|development|experimental`), `maturity`, `description`, `runtime_profile` (points into the profiles map above), `supports_load_mode`, `features` (`interactive|server|models`, each `supported|experimental|unavailable`), and optional `backend_config.recommended_use` (fork-specific validated model/quant/server-defaults pairing, e.g. the EngramHalo and HRX-staging entries).
- `settings.py` confirms the exact `~/.config/ai-toolbox-cockpit/config.json` mechanics: `config_path()` honors `$XDG_CONFIG_HOME`; `load_settings()`/`save_settings()` do plain `json.load`/`json.dump`, **atomic write via `.tmp` + `chmod(0o600)` + `Path.replace()`**, silently returning `{}` (falling back to legacy `~/.llama-cockpit.conf`/`~/.ds4-cockpit.conf` migration) on any read error. Structure: top-level `active_platform: str`, `backends: {<backend_id>: {default_toolboxes: {<platform_id>: <toolbox_id>}, ...arbitrary per-backend keys}}`. **There is no lock file and no read-modify-write transaction across processes** — cockpit itself has no protection against two of its own processes racing on this file; brainrouter joining as a second writer inherits that same "last writer wins" property from upstream at best, and can make it materially worse in a specific way v1 did not consider: brainrouter (often run as a long-lived daemon, possibly under a service manager) and an interactively-invoked cockpit TUI can easily have **different effective `$HOME`/`$XDG_CONFIG_HOME`**, meaning "shared config" silently becomes "two different files with the same name," not a shared-write race — see Technical plan §4.
- `runtime/engines.py`: `inspect_containers()` runs `<engine> ps -a --format "{{.Names}}|{{.Image}}|{{.Status}}|{{.CreatedAt}}"` (pipe-delimited, includes `CreatedAt` — brainrouter's current tab-delimited format omits `CreatedAt` and derives dates a different way). `runtime/images.py`: pure command builders (`pull`, `image inspect`, `rm -f`, `image rm`) plus `docker_hub_tag_url()`/`get_remote_image_date()`/`is_remote_image_newer()` — functionally identical in spirit to brainrouter's own `hub_toolbox_tag_dates()`/`image_created_date()`, just written for N images/backends instead of one. `runtime/server_process.py`: server launch is "`<engine> rm -f <container>` (best-effort) → `Popen(command)` in foreground → on exit/Ctrl+C, `<engine> rm -f <container>` again", with a `redact_command()` helper that scrubs `--api-key`/`HF_TOKEN` before ever printing/logging the command. This foreground-with-cleanup pattern does not map 1:1 onto brainrouter's server (which is a long-running HTTP daemon, not a TUI that can "suspend" for a foreground child) — see Architecture and flows.

## Technical plan

### 1. Naming decisions — three axes, not two (revised in v2)
v1 collapsed "engine" into a single reused column. The Dory critic correctly pointed out that cockpit's `runtime_profile` strings (`amd-rocm-hipblaslt`, `halogen-strix-halo`, `intel-level-zero`, ...) are finer-grained than the existing 8-value `runtimes.backend` enum and don't map onto it 1:1. Resolving this requires **three** distinct, separately-named concepts, not two:
1. **`toolbox_backend` / `serving_backend`** (user-facing "Backend") = *which toolbox/serving product* (`llama_cpp | ds4 | halogen | vllm | r9v`, matching cockpit's `BACKEND_IDS` minus `comfyui`). Chosen name avoids colliding with the pre-existing, semantically different `runtimes.backend` column and with `routing_profile`'s unrelated "backend" concept.
2. **`compute_api`** (user-facing "Engine", the literal `vulkan | rocm` the requirement names) = the existing `runtimes.backend` CHECK column (`cpu/cuda/rocm/vulkan/metal/sycl/rpc/other`). This is the granularity the user's literal ask ("engine: vulkan/rocm") actually matches — reuse it as-is for the benchmark/Sankey-facing "Engine" dimension; do **not** try to make it carry the finer profile strings too.
3. **`runtime_profile_id`** = cockpit's full profile string (`amd-rocm-hipblaslt`, `halogen-strix-halo`, etc.) from `toolboxes.json`'s `runtime_profiles` map. This is **not** exposed as a benchmark/Sankey "Engine" axis — it is an internal field used only for toolbox deployment (looking up `engine_args` to pass to container creation, Technical plan §5). Keeping it separate from `compute_api` avoids conflating "which podman flags to use to launch this toolbox" (deployment-time, high cardinality) with "which coarse accelerator API this run used" (analysis-time, the axis the user actually asked to chart).

Cockpit's own `ContainerEngine` (`podman`/`docker`) is a **fourth, unrelated axis** ("which container tool wraps the process") — brainrouter already only supports podman/toolbox; this plan keeps that constraint and does not add Docker/Distrobox support. Flagged explicitly so nobody conflates any of "engine" (compute API), "engine" (container runtime), or "runtime_profile" (deployment recipe) while implementing.

### 2. Data model (Rust) — revised in v2 for lossless catalog parsing
v1 proposed a single closed 5-variant `ToolboxBackend`/`ModelPayload` enum. Both the Dory readiness and critic reviews independently flagged this as a genuine contradiction with requirement 1 ("future ones" + "exclude comfyui, not fail on it"): a closed enum either hard-fails `serde` on `comfyui`/an unknown 7th backend, or silently drops the whole catalog entry, neither of which satisfies "brainrouter never breaks when upstream adds a backend." v2 splits this into two layers:

```rust
/// Backend identifier exactly as it appears in the catalog JSON. Open/lossless:
/// unknown or excluded ids round-trip instead of failing to parse. NOTE: serde's
/// built-in `#[serde(other)]` fallback discards the original string, which is not
/// good enough here (we need the literal id for display/debugging) — this needs a
/// custom `Deserialize` impl (deserialize to `String` first, then match) rather
/// than a derive; called out explicitly so it isn't "discovered" mid-implementation.
#[derive(Clone, Debug, PartialEq, Eq, Serialize)]
pub enum CatalogBackendId {
    LlamaCpp, Ds4, Halogen, Vllm, R9v,
    Comfyui,          // parsed, never surfaced in any UI/API list per requirement 1
    Other(String),    // any future backend id upstream adds before brainrouter has code for it
}

/// The narrower, closed set of backends brainrouter can actually *execute* actions
/// for (create/update/pull/server-launch). `Comfyui` and `Other` convert to `None`
/// here — they can still be *listed* (via `CatalogBackendId`) but never acted on.
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum SupportedServingBackend { LlamaCpp, Ds4, Halogen, Vllm, R9v }
impl TryFrom<&CatalogBackendId> for SupportedServingBackend { /* Comfyui | Other(_) -> Err */ }

pub struct RuntimeProfile { pub id: String, pub engine_args: Vec<String> } // from toolboxes.json.runtime_profiles
pub struct ToolboxDefinition {
    pub id: String, pub backend: CatalogBackendId, pub name: String, pub container_name: String,
    pub group: String, pub image: String, pub channel: Channel, pub maturity: Maturity,
    pub description: String, pub runtime_profile: String, pub supports_load_mode: bool,
    pub features: ToolboxFeatures, pub backend_config: Option<serde_json::Value>, // recommended_use etc, kept loose
}
pub struct ToolboxFeatures { pub interactive: FeatureState, pub server: FeatureState, pub models: FeatureState }

/// Catalog-level, always parses (any backend). `payload` is only `Some` for the
/// five supported backends; comfyui/unknown entries keep their `raw` JSON for
/// display/debugging but are never converted into an actionable ModelPayload.
pub struct CatalogModelEntry {
    pub id: String, pub backend: CatalogBackendId, pub name: String,
    pub raw: serde_json::Value,
    pub payload: Option<ModelPayload>,
}
pub enum ModelPayload { LlamaCpp(LlamaCppModel), Ds4(Ds4Model), Halogen(HalogenModel), Vllm(VllmModel), R9v(R9vModel) }
```
`ModelPayload` stays a per-backend enum (v1's reasoning here held up under review) because `catalog/schema.py` proves the five supported backends' model entries are structurally incompatible (r9v needs pinned commit SHA + file-role manifest + PLE hash; halogen needs `.hgn` checkpoint/overlay/tokenizer_dir; llama_cpp needs `inference_profiles`/`toolbox_defaults`/`auxiliary_downloads`) — directly mirroring why cockpit itself uses `ai_toolbox_cockpit/backends/<backend>/` per-backend modules rather than one generic backend. What changed in v2 is only the *outer* layer (`CatalogBackendId`/`CatalogModelEntry`) becoming open/lossless so the catalog itself never fails to parse.

DB: no changes to `models`/`artifacts`/`runtimes`/`experiments`/`runs` are required for *toolbox management* itself (that's catalog + live podman state, not historical experiment data) — a new **non-benchmark** table set (below) tracks brainrouter's own toolbox/model inventory state; the *benchmark* schema changes are scoped separately (§7).

New tables (own migration, e.g. `migrations/0003_toolbox_catalog.sql`):
```sql
CREATE TABLE toolbox_catalog_snapshot (
  id TEXT PRIMARY KEY,           -- e.g. content hash of vendored catalog files
  models_json TEXT NOT NULL,     -- raw vendored models.json, kept verbatim for audit/debug
  toolboxes_json TEXT NOT NULL,  -- raw vendored toolboxes.json
  source_commit TEXT,            -- upstream ai-toolbox-cockpit commit this snapshot was synced from
  synced_at TEXT NOT NULL
);
```
This table needs an explicit owning store and migration-runner registration (see §7's migration-runner finding — the same hardcoded-version-gate problem applies to any new SQLite file/migration, not just the benchmark one; if this table lives in the *same* `benchmark.db`, it must be added to `src/benchmark.rs`'s version gate; if it lives in its own DB file, that file needs its own (much simpler, since it's new) migration runner. Decision needed — see Open questions.
Live container state (what's installed/running) is **not** persisted to SQLite — mirrors brainrouter's existing pattern of asking podman live (`toolboxes_list()`), which is already proven correct/simple; we extend that function rather than duplicating state into a DB table that could drift from reality.

### 3. Catalog sync mechanism — **vendor**, not periodic runtime fetch (unchanged from v1, reaffirmed)
Rationale (sycophant-challenged in Alternatives): the catalog JSON is schema-validated, versioned (`schema_version`), and used to *build UI forms and validation*, not just to display "is there an update." A runtime fetch means brainrouter's UI shape can change under a user's feet with no review, and it adds a hard runtime dependency on GitHub being reachable from the host, which the current design explicitly does not have (brainrouter works fully offline for everything except image-update checks). Proposal:
- A `scripts/sync-toolbox-catalog.sh` (or `xtask`) fetches `ai_toolbox_cockpit/assets/{models,toolboxes}.json` from a **pinned upstream commit/tag** of `kyuz0/ai-toolbox-cockpit`, validates them against a Rust port of the *shape* of `catalog/schema.py`'s checks (not a full port of the Python — just enough structural validation to fail loudly on a schema change we don't understand yet, **and, per §2, treating an unrecognized `backend` id as a warning, not a hard validation failure**, so the sync script itself doesn't become the thing that breaks lossless parsing), and writes them into `assets/cockpit-catalog/{models,toolboxes}.json` + the pinned commit SHA into a `assets/cockpit-catalog/SOURCE` file, committed to the brainrouter repo.
- A scheduled CI job (weekly, mirroring the cadence implied by cockpit's own CalVer auto-tagging) re-runs the sync script and opens a PR if the content changed, so a human reviews every catalog update before it ships — this is the brainrouter-repo-level analogue of `hub_toolbox_tag_dates()`, but for catalog *content* rather than *image tag freshness*.
- The **existing** `hub_toolbox_tag_dates()`/"update available" runtime check is kept as a true periodic *runtime* fetch (per the existing pattern) and is **extended** to loop over every vendored toolbox's `image` field instead of the one hardcoded string — this part legitimately should stay live/periodic, because "is a newer tag available" is inherently a live fact, not a reviewable content change. **New in v2, from critic finding #12 (important):** this fan-out from 1 image to N images/backends turns a currently-unbounded, no-timeout call (`hub_toolbox_tag_dates()`, `src/server.rs:1839-1858`, confirmed no timeout set today, and the dashboard polls `/api/toolboxes` every 30s per `main_dashboard.html:2602-2608,2832-2835`) into a real scalability/rate-limit/registry-compatibility problem. Proposed fix: a small cached async image-metadata service — per-image TTL cache (e.g. 15–30 min), bounded concurrency, an explicit per-call timeout (reusing the existing `VERSION_CLIENT` pattern at `src/server.rs:71-79`, which supports per-call-site timeouts but isn't itself timeout-defaulted), a real OCI image-reference parser (not a Docker-Hub-only assumption), and a "freshness unavailable" status for registries the parser/adapter doesn't recognize, instead of silently treating every image as Docker-Hub-hosted.

### 4. Config.json merge design — revised in v2 (narrower default, explicit path-mismatch safeguard)
v1 proposed unconditional bidirectional read-modify-write against the shared file as the default. The Dory critic argued (and this document now agrees) that doing continuous, automatic background read-modify-write against a file a second live process (interactively-run cockpit) may be concurrently writing — with **no** lock, version, or conflict signal on either side — is a materially riskier promise than the user's "ideally merging" phrasing requires, especially compounded by the HOME/config-path mismatch risk below. v2 default:
- **Phase 1 (this rollout): read-only import.** brainrouter reads `~/.config/ai-toolbox-cockpit/config.json` (same path resolution as cockpit: `$XDG_CONFIG_HOME` default `~/.config`) at startup/on-demand and honors `active_platform`/`backends.*.default_toolboxes` to seed its own UI defaults. Never writes automatically.
- **Explicit, user-triggered write action** ("Apply to cockpit config" button/CLI flag): when the user explicitly asks brainrouter to persist a change back, brainrouter does a single reload-verify-write (load current file → apply only the specific key(s) the user changed → write back atomically, same `.tmp` + `chmod(0o600)` + `rename()` contract as cockpit's `save_settings()`) — an explicit user action in the loop, not a hidden background sync. brainrouter **only ever touches the same keys cockpit already owns** (`active_platform`, `backends.<id>.default_toolboxes.<platform_id>`) plus, if needed later, a namespaced `backends.<id>.brainrouter` sub-object — never a top-level brainrouter-only key, and all other keys round-trip untouched.
- **True bidirectional live-merge (both tools writing at any time, safely) is explicitly deferred** pending either upstream cockpit adopting a lock/version field, or the user accepting the documented last-writer-wins risk for the automatic case specifically (this is now an Open question, not a v1-style "accepted risk" footnote — the user should decide whether Phase-1-read-only is an acceptable interpretation of "ideally merging," or whether they want the riskier automatic bidirectional behavior anyway).
- **New in v2 — config path/owner mismatch:** the daemon's process `$HOME` (which can silently fall back to `/root` when unset — already partially flagged by an existing startup warning at `src/daemon.rs:284-286`) is not guaranteed to match the interactive user's `$HOME` that actually runs cockpit, especially if brainrouter runs as a system service under a different user/account. If they differ, "shared config" silently becomes two different files with the same name and no error. Proposed mitigation: (a) surface the **effective resolved path** (and its owning UID, if determinable) for the config file prominently in the dashboard/CLI wherever cockpit-config state is shown, so a mismatch is visible rather than silent; (b) add an explicit config-path override setting (env var or brainrouter YAML config key) for operators who know brainrouter and cockpit run under different accounts; (c) refuse to *create* the file autonomously when running as a system-managed service account (heuristic: e.g. UID 0 or a dedicated service UID) — only auto-create it for an interactively-invoked brainrouter process.
- **Resolved in v3 (was Open question 2):** TOP SESSION selected option (a) — if `~/.config/ai-toolbox-cockpit/` (or its resolved equivalent, per the path-mismatch mitigation above) does not exist on a given host, brainrouter **leaves it absent** and operates entirely on its own built-in defaults until cockpit itself initializes that directory (by being run at least once on that host). brainrouter never auto-creates the directory or an empty `config.json`, and never refuses to manage toolboxes because the directory is absent — absence is a normal, first-class state, not an error. This directly answers "what happens if cockpit isn't installed on a given host" from the original requirements: brainrouter is fully functional without it, and the explicit single-write "apply" action (above) is simply unavailable/disabled (not erroring) until the directory exists.

### 5. Native Rust create/update/pull for ds4/halogen/vllm/r9v (mirroring cockpit's `runtime/` patterns, not porting Python)
- Generalize today's `toolboxes_list()`/`upgrade_toolbox()` to operate over the vendored catalog's `toolboxes[]` array instead of one hardcoded image/container name; container listing gains the `CreatedAt` field (adopt cockpit's `ps -a --format "{{.Names}}|{{.Image}}|{{.Status}}|{{.CreatedAt}}"`, pipe-delimited to avoid tab-in-status edge cases) so per-toolbox local-vs-remote freshness works for all of them, not just one.
- **New in v2 — container ownership labeling:** every toolbox container brainrouter creates gets podman labels (`io.brainrouter.managed=true`, `io.brainrouter.catalog_id=<toolbox id>`, `io.brainrouter.catalog_revision=<snapshot id>`) so brainrouter only ever mutates/deletes containers it created. A pre-existing container (e.g. one cockpit created before brainrouter was ever run against this host) is shown as **unmanaged** and requires an explicit "adopt" action before brainrouter will touch it — prevents brainrouter silently deleting/recreating a container the user is actively using via cockpit.
- **New in v2 — operation locking and idempotency:** create/update/delete become **destructive** operations (see §9, Security) that must not run concurrently against the same container name (single in-flight-mutation-per-name lock, e.g. a `tokio::sync::Mutex` keyed by container name, or a DB-backed lease if multiple brainrouter processes can front the same podman socket). Status responses are idempotent: "already running"/"already stopped"/"already deleted" are treated as success, not error, matching how a retried dashboard click should behave.
- **`create`/`update` sequence — flagged as unverified, needs a spike (Dory critic blocking finding #5):** v1 asserted the existing `pull → rm --force → toolbox create --image` sequence (already proven for the one llama.cpp/Vulkan image, which needs no extra flags) generalizes to every backend by parameterizing `--image` and threading `runtime_profile.engine_args` (raw podman flags like `--device`, `--group-add`, `--security-opt`, `--env`) into the same `toolbox create` invocation. **This has not been verified against real `toolbox` CLI behavior.** `toolbox create` (the Fedora/RedHat toolbox wrapper, currently invoked with only `--image <image> <name>` at `src/server.rs:2283-2293`) has its own, more limited flag surface than a bare `podman create`/`podman run`, and it is not confirmed here whether it forwards arbitrary podman flags like `--device`/`--security-opt`/`--group-add` at all. Before claiming parity for any backend that needs non-default `engine_args` (R9V's ROCm device passthrough is the clearest case), this needs a concrete spike: run `toolbox create --help` / test against a real host, and if `toolbox` cannot forward the needed flags, switch the **deployment primitive** for non-default-profile toolboxes from the `toolbox` wrapper to direct named `podman create`/`podman run` (which definitely supports these flags natively), keeping `toolbox` only where its opinionated defaults are sufficient (the current Vulkan/default-profile case). This decision is deliberately left open pending that spike — see Open questions and Alternatives.
- **"Enter" (cockpit's interactive Toolbx/Distrobox shell) has no web-dashboard equivalent** — a browser cannot attach to a live TTY the way a TUI can suspend itself. Proposed: brainrouter's dashboard exposes the exact `toolbox enter <name>` command as copy-to-clipboard text. The CLI (`brainrouter cli toolbox enter <name>`) can genuinely exec it **only when the CLI and the daemon/container engine are on the same host and user context** — **new in v2**, correcting a gap the Dory critic found: since the CLI can target a remote daemon via `--url` (`src/cli.rs:5-6,23-32,339-347`), blindly `exec`ing `toolbox enter` locally when the CLI is talking to a *remote* daemon would enter the wrong (local, likely nonexistent) container, or fail confusingly. The CLI must detect same-host-same-user (e.g. comparing to a UDS-only invocation, or an explicit `--url` pointing at `localhost`/the local UDS) before offering to exec directly; otherwise it prints the exact command as non-executable copy/paste guidance, identical to the dashboard's behavior. Never silently offer a false remote-TTY capability.
- Server-mode launch (per-backend `llama-server`/DS4/vLLM/R9V/Halogen command construction) is **not** cockpit's foreground-Popen-with-Ctrl+C-cleanup model — brainrouter is a long-running daemon, so server-mode toolboxes should be launched as **detached, named, brainrouter-managed containers** (`podman run -d --name <container> ...`) that brainrouter can start/stop/status via the dashboard, analogous to how brainrouter already manages the primary llama-swap-fronted server, rather than a foreground process the dashboard process would have to babysit. This is a genuine architecture divergence from cockpit and is called out as a decision needing sign-off (Open questions) since it changes the operational model (who kills the container if brainrouter restarts, log capture, etc.) — mitigated by the ownership labeling above (brainrouter reconciles/adopts its own previously-created named containers on startup rather than assuming a clean slate).
- Each backend gets its own command-builder module (`src/toolbox_catalog/backends/{ds4,halogen,vllm,r9v}.rs`) mirroring cockpit's `backends/<backend>/` split — **not** shared generic code — because schema.py already proves the five backends need different required fields/validation, and README confirms "the vLLM catalog imports the toolbox's model launch recipe rather than replacing it with generic defaults." Phase order (see Rollout) starts with the backend-agnostic Toolboxes-tab parity (works for all 5 without per-backend server-launch code), then adds server-launch command builders one backend at a time.

### 5a. The `--name` fix, precisely (do first, small, independent — but the mechanism is corrected in v2)
Re-verified directly against `src/server.rs:1886-1909`: the version-check runs `podman run --rm <image> llama-server --version` wrapped in `tokio::time::timeout(Duration::from_secs(PODMAN_VERSION_TIMEOUT_SECS /* 15 */), child)` with `.kill_on_drop(true)` set on the `Command`. On a *normal* exit, `--rm` alone is sufficient — the Dory critic is right that a missing `--name` does not, by itself, explain a leak on the happy path. The credible leak mechanism is the **timeout branch**: when the 15s timeout fires, `kill_on_drop` sends a kill signal to the `podman run` client process; if that signal terminates the client before it completes its own `--rm`-triggered container teardown, the underlying container can be orphaned — and because it was never given a name, it surfaces in `podman ps -a` under a random pet-name with no way to correlate it back to "the version check that timed out." Fix (both parts needed):
1. Add a deterministic `--name brainrouter-version-check` (or per-invocation-unique if concurrent version checks are possible — needs a decision, see Open questions) **and** `--replace` (atomically removes any stale same-named container first, so a previous orphan doesn't cause a "name already in use" error on the next check).
2. On the timeout branch specifically, after `kill_on_drop` fires, issue a best-effort `podman rm -f <name>` before returning the timeout error, so a timeout-orphaned container is actively cleaned up rather than merely "now easier to find manually."
Regression test must **force the timeout branch** (e.g. inject an artificially low timeout against a slow/blocked command, or a test double) and assert no container survives — v1's proposed test ("run the check twice, assert count unchanged") only exercises the normal-exit path, which the critic correctly noted was never the reported failure mode in the first place.

### 5b. Routing/provider integration — new required prerequisite (Dory critic blocking finding #4)
v1 assumed that once a server-mode toolbox container is running, the Sankey diagram and benchmark system could simply be told to reflect its "backend"/"engine" as first-class dimensions of real traffic. This is not true today: `src/daemon.rs:305-320` constructs the single shared `Router` from exactly `classifier`, `manifest`, and `llama_swap` — there is no generic "list of providers" concept, and `RouteEvent` (`src/routing_events.rs:30-82`) only ever carries data about requests that flow through that fixed set. A detached toolbox-server container launched from the new Toolboxes/Server-mode UI is, as of today, **completely invisible to the router** — starting a DS4 server through brainrouter's new UI does not make brainrouter route any request to it.
Proposed minimal fix (deliberately **not** a full routing-parity rewrite, which is out of scope — see Non-goals): introduce a lightweight **"serving identity" registration** — when a toolbox server-mode container starts, it registers a `{toolbox_backend, compute_api, runtime_profile_id, endpoint}` record that either (a) is added as an additional llama-swap-compatible upstream (if the launched server speaks an OpenAI-compatible API, which llama.cpp/vLLM do, and DS4/Halogen need to be checked against), making it genuinely routable and therefore honestly populate `RouteEvent`/Sankey/benchmarks, or (b) for backends that can't be added as a routable upstream yet, is exposed only as **standalone server status** (dashboard shows it running, no Sankey/routing claim is made about it) — explicitly not faking Sankey data for traffic that never went through the router. Which backends land in (a) vs (b) first is a per-backend implementation detail resolved during the Rollout's server-mode phases, not asserted uniformly here. This sub-phase is a **prerequisite** for the Sankey PR (Rollout is reordered accordingly) — shipping the Sankey columns before this exists would either show columns that are always empty/n-a, or (worse) require a stopgap "fake it" data source, neither of which was the ask.

### 5c. PR2 API contract and implementation decisions (added during PR2 implementation, 2025-09-17)
This section resolves the "needs its own API-contract note before PR2 starts" gap flagged in earlier drafts, and records the decisions made while implementing the typed catalog layer + generalized Toolboxes tab.

**Typed catalog layer** landed in `src/toolbox_catalog/{types,models}.rs` exactly as sketched in §2, with one refinement: rather than modeling every optional per-backend field (llama_cpp's `inference_profiles`/`dspark`/`mtp`/`vision_projector`/`auxiliary_downloads`, vllm's `extra_flags`/`env`/`ctx`, etc.), each `ModelPayload` variant strongly types only the fields proven common across **every** vendored entry for that backend (verified by intersecting keys across all entries, not just inspecting one), and captures the rest via `#[serde(flatten)] extra: serde_json::Map<String, Value>`. This keeps `ToolboxDefinition::backend_config`'s "kept loose" philosophy consistent across the whole typed layer instead of applying it to one field and guessing shapes everywhere else. `CatalogModelEntry.raw` still holds the full original JSON regardless, so nothing is lost even where `extra` is used instead of a named field.

**Migration decision (resolves part of §2's "Decision needed"):** `migrations/0003_toolbox_catalog.sql` / `toolbox_catalog_snapshot` is **not created in PR2**. PR2's toolbox/container management needs no new persisted state — the catalog is embedded at compile time (PR1) and container state is read live from podman (unchanged pattern, extended to all 5 backends), matching §2's own observation that "live container state is not persisted to SQLite." A `toolbox_catalog_snapshot` table only becomes useful once something needs to *look back* at which catalog snapshot was in effect for a historical action (the clearest case: §7's benchmark toolbox-family dimension anchoring a run to the snapshot that was current when it happened). That need is revisited at Rollout PR 5, not introduced speculatively here.

**Container ownership labels and the adopt flow.** Podman labels are set at container-creation time and cannot be attached to an already-created container in place — there is no `podman label add`. This has a direct consequence for "adopt": adopting a pre-existing, unmanaged container that happens to match a catalog `container_name` cannot mean "tag it in place." Two options were available: silently treat any name/image match as brainrouter-owned (rejected — this is exactly the risk §5 called out, brainrouter could then delete/recreate a container the user is actively driving via cockpit without ever having asked), or make "adopt" an explicit **recreate-in-place** operation that removes the existing container and immediately recreates it from the *same* image (no forced pull) with brainrouter's ownership labels attached. This PR takes the second option: `POST /api/toolbox-containers/{name}/adopt` is really "recreate this container, unchanged image, now labeled" — it is destructive (briefly stops/removes the container) and is presented to the user as such, not as a free no-op relabel. `update` is the same recreate primitive parameterized to also pull the newest image first; `create` is the same primitive with no prior container to remove.

**`toolbox create --label ...` support is unverified — attempted, fails loud, not silent (narrower cousin of §5's finding #5).** Creation/recreation keeps using `toolbox create --image <image> <name>` (unchanged primitive, still the one proven-working invocation, and needed so containers stay compatible with the future `toolbox enter` "Enter" parity feature from §5 — switching to a bare `podman create` would define away that compatibility without ever deciding to). Whether `toolbox create` forwards a `--label k=v` flag through to the underlying `podman create` the way the ownership labels need is **not verified in this environment** (no `toolbox`/`podman` binary available to test against, same limitation as the R9V spike). This PR's stance: pass `--label io.brainrouter.managed=true --label io.brainrouter.catalog_id=<id> --label io.brainrouter.catalog_revision=<rev>` to every `toolbox create` call and let it fail loudly (a normal `500` with the real `toolbox`/podman stderr, exactly like any other create failure) if the flag isn't supported — this is a visible, immediate, unambiguous failure a real host will surface the first time PR2 runs there, not a silent mis-tagging. If it does turn out to be unsupported, the fallback (switching the creation primitive to `podman create` for brainrouter-managed containers, accepting the `toolbox enter` compatibility question that comes with it) is deferred to whoever hits that failure first, not preemptively built here. `catalog_revision` is a short (12 hex char) SHA-256 prefix over the two vendored catalog files' bytes (`toolbox_catalog::vendored_catalog_revision()`), not a reference to a persisted snapshot row, consistent with the "no new DB table in PR2" decision above.

**Ownership determination without labels on unmanaged containers:** since an *unmanaged* container has no `io.brainrouter.*` labels by definition, "managed" is computed as "container exists AND carries `io.brainrouter.managed=true`" (read via `podman inspect --format '{{ index .Config.Labels "io.brainrouter.managed" }}'`), never inferred from name/image matching alone.

**Per-container locking.** A `tokio::sync::Mutex<()>` keyed by container name, held in `AppState` as `toolbox_container_locks: Mutex<HashMap<String, Arc<tokio::sync::Mutex<()>>>>` (outer std lock only guards inserting a new per-name entry; the actual create/update/delete/adopt work holds the per-name async lock for its duration). A lock is acquired for the container's `container_name` before create/update/delete/adopt run, and released after; a second concurrent request for the same name queues behind it rather than racing `podman`/`toolbox` invocations against each other. Different container names never contend.

**API routes (all under the existing destructive-route gate for POST; GET routes are read-only and ungated, matching `/api/toolboxes` today):**
- `GET /api/toolbox-catalog` → `{ "schema_version": <i64>, "toolboxes": [ToolboxDefinition, backend restricted to the 5 supported ids — comfyui entries are omitted entirely, not merely unsupported-flagged], "platforms": [Platform] }`. Read-only view of the vendored catalog, scoped to what brainrouter can act on.
- `GET /api/toolbox-containers` → `{ "containers": [{ "container_name", "toolbox_id": string|null, "backend": string|null, "image", "running": bool, "status", "created_at", "local_created", "latest_created", "update_available": bool, "managed": bool }] }`. Generalizes today's `/api/toolboxes`: instead of filtering to a `llama-*` name prefix, every podman container (`podman ps -a`) is correlated by exact name against every supported-backend toolbox's `container_name` in the catalog; a podman container matching no catalog `container_name` is omitted (same effective behavior as today's prefix filter, generalized to be catalog-driven instead of hardcoded). `toolbox_id`/`backend` are `null` only in the (should-not-normally-happen) case a name matches but the matching catalog entry was somehow not resolvable; in practice they mirror the matched `ToolboxDefinition`.
- `POST /api/toolbox-containers` body `{ "toolbox_id": "<catalog id>" }` → creates the named container for that catalog entry (must not already exist; use `update`/`adopt` otherwise). Locked per container name.
- `POST /api/toolbox-containers/{name}/update` → pulls the catalog entry's current `image` and recreates. Locked per container name.
- `POST /api/toolbox-containers/{name}/delete` → force-removes the container. Idempotent: removing an already-absent container returns `200 {"status":"ok","message":"already removed"}`, not an error.
- `POST /api/toolbox-containers/{name}/adopt` → recreate-in-place as described above (no pull). Rejects (`409`) if the container is already `managed`.
- `GET /api/toolbox-models` → `{ "schema_version": <i64>, "backends": [ModelBackendCatalog, restricted to the 5 supported backend ids] }`. Read-only catalog view; no download/install action exists yet (that's Rollout PR 6's explicitly-flagged-as-undesigned download lifecycle, Open question 5).
- All five mutating routes are added to the destructive-route allowlist (`src/server.rs`'s `is_destructive` check) via a `path.starts_with("/api/toolbox-containers")` clause (mirrors the existing `/api/upgrade/` pattern) rather than being enumerated one-by-one, since new sub-paths under this prefix are expected as this rollout continues.

**Existing routes kept, not removed, for backward compatibility this PR:** `/api/toolboxes` and `/api/upgrade/toolbox[/…]` continue to work exactly as before (llama_cpp/Vulkan only) — they are not deleted in PR2. The dashboard's Toolboxes tab is switched over to the new catalog-driven routes; the old routes remain callable (e.g. by any external script depending on them today) but are noted as superseded, to be removed in a later cleanup PR once nothing depends on them.

### 6. Sankey diagram extension
- Add fields to `RouteEvent` (`src/routing_events.rs:30-82`, corrected citation) — `toolbox_backend: Option<String>` and `compute_api: Option<String>` (naming per §1) — populated only for requests that actually flow through the router-registered serving identities from §5b; everything else (cloud-routed requests, non-toolbox-served requests, and — until §5b lands for a given backend — server-mode containers not yet wired in) falls back to an explicit bucket.
- **New in v2 — explicit bucket vocabulary, not a single ambiguous "n/a"/"cloud" catch-all** (Dory critic nit, adopted because it materially affects Sankey readability): use distinct, stable values — `cloud` (routed to a cloud/hosted provider), `local_unmanaged` (served by a local process/container brainrouter didn't create or isn't tracking), `external` (a toolbox-like backend the user pointed brainrouter at manually, outside the catalog), `unknown` (genuinely indeterminate) — rather than collapsing all of these into one bucket for UI convenience, which would misrepresent genuinely different situations as the same thing.
- `SK_COLS` grows to 6 entries; `skKeysOf()` grows to return `c4`/`c5`; `keys` array, `skColorFor()`'s per-column color map, and `matchesSankey()`'s `'c' + col` lookup already generalize (confirmed: the click-filter mechanism is column-index-generic) — only the hardcoded literal column count/positions and the color table need new entries, not a redesign.
- Column x-positions and `SK_TOTAL_W` need recomputing for 6 columns; propose measuring/laying out columns proportionally from `SK_COLS.length` instead of hardcoded per-column `x` literals, so a 7th future column doesn't require another hand-edit of pixel constants — flagged as a small refactor bundled into this change since we're touching every line that assumes 4 anyway.
- Nodes with no backend/engine get one of the explicit buckets above (never silently dropped), so the diagram's total flow count still balances across all 6 columns.
- **Dependency (new in v2):** this PR is now explicitly ordered **after** §5b (routing/provider integration) in the Rollout — shipping it earlier would mean the two new columns are populated almost entirely by the fallback buckets, which is technically honest but not what "extend the Sankey with backend/engine" was asked for.

### 7. Benchmark schema/UI extension
- **No new column for "Engine"** — reuse `runtimes.backend` (already `cpu/cuda/rocm/vulkan/metal/sycl/rpc/other`), per §1's three-axis resolution; audit and fix any import/ingest path that isn't currently populating it correctly for toolbox-served runs (needs verification during implementation, not assumed here).
- **New dimension needed: "which toolbox family served this run"** — **left as an explicit open design decision in v2, not asserted**, because the Dory critic showed the v1 approach (`ALTER TABLE runtimes ADD COLUMN toolbox_family ...`) runs into `runtimes`' existing `NOT NULL` llama.cpp-specific columns (`repository`, `fork_name`, `commit_sha`, `compiler`, `compiler_version` — `migrations/0001_benchmark_explorer.sql:50-64`) and its existing uniqueness constraint, neither of which was designed with non-llama.cpp-fork backends in mind. Two candidate approaches, presented for a decision rather than picked unilaterally:
  - **(a) Widen `runtimes`:** make the llama.cpp-specific columns nullable, widen the uniqueness constraint to include `toolbox_family`/`toolbox_id`, and add a migration that backfills/validates existing rows. Simpler schema (one runtimes concept), but changes the meaning/constraints of an existing, populated table and requires care around the `run_summary` view and every existing query that assumes those columns are always present.
  - **(b) New `serving_runtimes` table:** keep `runtimes` exactly as-is (llama.cpp/native-binary benchmark identity, unchanged), add a separate table for non-llama.cpp-fork serving stacks (ds4/halogen/vllm/r9v), and give `experiments` a second, nullable FK (`serving_runtime_id`) alongside the existing `runtime_id`. Avoids touching a stable existing table's contract, at the cost of two similar-but-different "what served this run" concepts existing side by side (more surface area, clearer boundaries).
  - Both approaches need `toolbox_id`/`toolbox_family` anchored against a **catalog revision** (`catalog_snapshot_id`/`source_commit`, from §2's `toolbox_catalog_snapshot` table), not just a bare string id — the Dory critic correctly noted that catalog ids/entries can be renamed or removed upstream over time, and a historical benchmark row referencing a since-renamed id becomes ambiguous without an anchor to the exact catalog snapshot that was in effect when the run happened.
- **Migration-runner wiring is a required, concrete implementation step, not a side effect of adding a `.sql` file** — re-verified in v2 directly: `src/benchmark.rs:1895-1953` hardcodes acceptance of schema versions 1–2 only, with exact table-count checks (`required_v1_tables != 5`, `required_tables != 6`) and returns `BenchmarkError::Validation` otherwise. Whichever approach (a)/(b) is chosen, this function's version gate must be extended to recognize the new version (and its own new expected-table/column-count check) — the migration literally will not run without this, regardless of how correct the `.sql` file is.
- `RuntimeDefinition` (`src/benchmark.rs`) and/or a new `ServingRuntimeDefinition` gains the fields chosen above; `RunSummary`/`run_summary` view exposes them; `/api/benchmarks/filters` and `/api/benchmarks/runs` gain corresponding filter params.
- Import paths (`llama-bench` ingest and the generic `/api/benchmarks/ingest`) accept optional `toolbox_family`/`toolbox_id` in the experiment/runtime template payload (not derived from the benchmark tool's own JSON output, which has no concept of it) — matches how `backend`/engine is already supplied via the runtime template today, not extracted from `llama-bench.json`. Ingest must also be re-checked against the widened/second-table uniqueness semantics chosen above so `INSERT OR IGNORE` cannot silently drop a row that should have been distinct (§ current-system finding, `src/benchmark.rs:2248-2273`).

### 8. Spider/radar chart (new) — token-efficiency metric substantially revised in v2; axis semantics resolved in v3
- New custom inline-SVG radar chart (consistent with the codebase's existing "no chart library" convention in `benchmarks.html`) added to `benchmarks.html` (or a new `spider.html` panel included from it), driven by a two-part picker UI (resolved in v3, replacing v2's undifferentiated "7 pickable dimensions" framing):
  - **Facet filters** (multi-select, narrow the underlying run population before comparison): engine, backend, toolbox. These never become their own radar axis.
  - **Compare-by / series selector** (which polygons are drawn): the user picks model and/or harness as the entity dimension(s) to compare — e.g. "compare 2-5 models" (one polygon per selected model, harness held fixed/aggregated by the facets above), "compare 2-5 harnesses" (same, inverted), or "compare model×harness pairs" (one polygon per distinct pair). Model/harness are therefore never radar axes either — they select *what* is being compared, not *how*.
  - **Metric axes** (the actual radar spokes — continuous only): token efficiency to positive result (TEPR) and speed at minimum; designed to be extensible to additional continuous metrics later (e.g. pass rate, cost-per-run) without changing this facet/series/axis structure. User picks ≥2 metric axes to plot (a 2-axis radar is a valid, if minimal, shape — noted here explicitly since it's an unusual radar UX, not a bug).
- **Resolved in v3 (was Open question 7 / "carried over from v1" in v2): categorical axes are never plotted as radar spokes.** TOP SESSION selected option (b) from v2's three presented alternatives: engine/backend/toolbox (and, by the same logic, model/harness) are filter/facet/series-selection keys only, determining which entities appear and which runs feed them, never plotted as a spoke themselves. This resolves what v2 left as a genuine unresolved product decision; option (a) (binary match/no-match expansion) and option (c) are no longer live alternatives for this rollout.
- Continuous axes (TEPR, speed, and any future metric axis) are independently normalized (min–max or percentile) across the currently filtered (faceted) run set — unchanged from v2.
- **"Token efficiency to positive result" (TEPR) — substantially revised in v2.** The Dory critic identified that v1's formula used `experiments.prompt_tokens`/`generation_tokens`, which on closer inspection are **declared/planned** token-budget fields set at experiment-setup time, not confirmed to be an **observed, per-attempt actually-consumed** count — a metric named "efficiency" that silently uses planned-not-actual numbers would be misleading. v2's proposal (still flagged for explicit user sign-off, not shipped as fact):
  > `TEPR(entity, cohort) = SUM(actual_tokens_consumed across every run attempt for entity within cohort) / COUNT(runs in cohort for entity where outcome = positive)`
  - **`actual_tokens_consumed` must be the observed count from the run/telemetry itself** (e.g. `telemetry_samples` or a per-run actual-usage field), **not** `experiments.prompt_tokens`/`generation_tokens` — this document explicitly does **not** assert which existing field (if any) already holds this correctly for every backend; confirming/adding the right field is now called out as a required implementation-time verification step, not assumed solved by picking a column name in this doc (Open question 6, left open per TOP SESSION's instruction to resolve at implementation time).
  - **One authoritative "positive" rule, not left ambiguous per multi-task run:** a run counts as positive only if `runs.status = 'succeeded'` **and**, when the run has any `quality_results` rows, **all** of them have `passed = 1`. A run with zero `quality_results` rows is **excluded from TEPR entirely** (not counted as pass or fail) rather than silently defaulting either way.
  - **Cohort restriction, new in v2:** TEPR is only ever compared within a matched cohort (same workload id at minimum) — mixing workloads in one TEPR number was flagged as making the metric meaningless, since token cost is workload-dependent by construction.
  - **Minimum sample size, new in v2:** TEPR is not displayed (shown as "insufficient data," not a misleadingly precise number) below a minimum combined pass+fail sample count for the entity/cohort pair (proposed default `n ≥ 3`, adjustable) — small-sample TEPR values are flagged as low-confidence even above that floor.
  - Undefined (`COUNT(positive)=0` within the cohort) is rendered as "no passing runs," not 0 or ∞.
  - **Rejected/alternative definitions, unchanged from v1, still offered to the user as alternatives if TEPR-as-now-defined isn't the intent:** (a) generation-tokens-only (excludes prompt cost — undercounts high-context harnesses); (b) per-success-run-only (ignores failed-attempt cost entirely — simpler, but is really "tokens per response," not "efficiency to a positive result"); (c) cost-normalized ($/token) — rejected for now, no local-compute pricing table exists.

### 9. Security boundary for the new mutation surface (new in v2 — Dory critic finding #15)
v1's "Security, privacy, reliability, and operations" section (kept below, largely unchanged) covered secrets/permissions but not the structural fact that this plan adds an entirely new class of privileged endpoints (create/update/delete/adopt for toolbox containers, server-mode start/stop, and — if the write half of §4 ships — config.json mutation). These are **not automatically covered** by the existing destructive-route allowlist: `src/server.rs:224-241` is a hardcoded path-prefix/exact-path match (confirmed by direct inspection) gating destructive APIs to loopback-only callers; a new route like `/api/toolbox-containers/{id}/delete` is reachable from non-local callers unless explicitly added to that list, which matters concretely because the daemon supports an optional non-loopback bind mode (`src/daemon.rs:144-153`). Required, concrete additions (not just "be careful"):
- Every new mutating route added to the same `is_destructive` allowlist mechanism (or its structural successor if that mechanism is refactored) — enumerated explicitly in Detailed implementation, not left to "whoever writes the route remembers."
- Secrets (`HF_TOKEN`, `--api-key`, any backend credential in `backend_config`/`config.json`) never appear in logs, command-line argv visible via `ps`, or API responses — reuse cockpit's `redact_command()` discipline as the baseline, verified with a test that asserts a secret-bearing command never appears unredacted anywhere observable.
- Containers created by this feature default to rootless/no-new-privileges unless a specific `runtime_profile.engine_args` entry requires otherwise (e.g. device passthrough for ROCm) — any such elevated flag is itself catalog-vendored and code-reviewed (§3), not user-supplied free text at request time.
- Config.json's write path (§4) is itself a destructive-route candidate and must be added to the same allowlist mechanism, not treated as "just a config file."

## Alternatives considered

**Catalog sync: vendor vs. runtime fetch.** *Rejected:* live runtime fetch of `models.json`/`toolboxes.json` on every dashboard load or on a timer, mirroring `hub_toolbox_tag_dates()`. *Why rejected:* those two files drive validation and form-generation, not just a freshness badge; an unreviewed upstream change could silently alter brainrouter's UI/behavior, and it adds a hard network dependency for core functionality that today works fully offline. *Chosen instead:* vendor + reviewed weekly sync PR (§3), keeping only true "is there a newer image" checks live (now with a caching/TTL/bounded-concurrency design, since the check now fans out to N images — §3).

**Config.json: bidirectional shared file vs. read-only import + brainrouter's own store.** *v1 chose:* full read-modify-write against the same file/format. *Revised in v2, superseded (see Decision log):* the Dory critic argued unconditional automatic RMW against a file a second live, unlocked process may be concurrently writing is riskier than the user's "ideally merging" ask requires, compounded by the HOME/config-path mismatch risk (§4). *Chosen instead:* Phase 1 read-only import + an explicit, user-triggered single-write "apply" action; true automatic bidirectional merge deferred pending either a jointly-supported protocol or explicit user sign-off that they want the riskier behavior anyway (Open questions). This is the most consequential change from v1 to v2 and is flagged for the user's explicit reaction, since it is a narrower interpretation of requirement 3 than v1 shipped.

**Toolbox model data: one generic struct vs. per-backend enum.** *Chosen (unchanged from v1, reaffirmed by review):* `ModelPayload` enum per backend, because `catalog/schema.py`'s validation rules for r9v/halogen/llama_cpp are structurally incompatible, directly mirroring cockpit's own `backends/<backend>/` code-organization decision. **New in v2:** the *outer* catalog-id/listing layer around this enum is now open/lossless (`CatalogBackendId`), not closed — see §2 — to fix the future-backend/comfyui parsing contradiction the closed-enum-only version had.

**Server-mode launch: foreground-suspend-TUI vs. detached daemon container.** *Chosen (unchanged from v1):* detached, named, labeled containers brainrouter can start/stop/inspect asynchronously, because brainrouter's dashboard is a long-running HTTP server with no TTY to suspend into on behalf of a browser tab. **New in v2:** this choice now has an explicit, load-bearing consequence spelled out (§5b) — detached containers are, by default, invisible to the request router, so the "populate Sankey/benchmarks from real traffic" promise requires the new registration sub-phase, not just "launch it and the columns will populate themselves."

**`toolbox create` vs. raw `podman create`/`podman run` as the deployment primitive (new in v2).** *Not yet decided — presented as a live alternative, not resolved unilaterally,* because whether `toolbox create` can forward the podman flags (`--device`, `--security-opt`, `--group-add`) that R9V's ROCm passthrough and similar profiles need is unverified (§5's blocking finding #5). If a spike shows `toolbox create` cannot forward these flags, the plan would switch to using bare `podman create`/`podman run` directly for any toolbox whose `runtime_profile.engine_args` needs flags `toolbox` doesn't support, keeping the `toolbox` wrapper only for the current default/Vulkan profile where it's already proven to work. Recorded here rather than picked so the spike's actual result drives the decision, not this document's guess.

**Benchmark schema: widen `runtimes` vs. new `serving_runtimes` table (new in v2).** *Not yet decided — presented as a live alternative* (§7) because the Dory critic showed both have real costs: widening risks changing an existing, populated, `NOT NULL`-constrained table's contract; a new table avoids that but adds a second "what served this run" concept side by side with the first. Flagged for a decision during PR planning for the benchmark-extension phase, informed by how disruptive each is once actually attempted against the existing `run_summary` view and its consumers.

## Security, privacy, reliability, and operations
*(High-level operational summary; §9 above has the concrete, load-bearing detail added in v2.)*
- `cockpit_config.rs` must preserve cockpit's `chmod 0600` on write (the file may contain `HF_TOKEN`/API keys per backend settings) — never relax permissions, never log the full file contents.
- Command builders must apply the same secret-redaction discipline as cockpit's `redact_command()` (`--api-key`, `HF_TOKEN`, etc.) before any command is logged or displayed in the dashboard/CLI.
- Detached server-mode containers need an operational answer for "what happens to a container if brainrouter itself restarts/crashes" — proposed: containers are named deterministically and labeled (§5), and brainrouter reconciles/adopts already-running named-and-labeled containers on startup rather than assuming a clean slate.
- Catalog vendoring must not vendor any auxiliary download credentials or model weights — only the catalog *metadata* JSON files.

## Rollout, migration, and rollback

1. **PR 0 — this design doc + the `--name`/timeout fix.** Design doc committed to `docs/design/ai-toolbox-cockpit-integration.md` (per Dory) as the durable source of truth; the corrected §5a fix (name + replace + timeout-branch cleanup) lands as a small, independent, safe-to-land-alone change with its timeout-forcing regression test.
